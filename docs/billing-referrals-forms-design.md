# Billing, E-Referrals & Forms - Design Doc (F11-F13)

> **Status / orientation.** This is the active design doc for **F11 (billing & coding assistant)**, **F12 (standardized e-referrals)**, and **F13 (forms & letters generator)**. It is the file the backlog index (`docs/feature-backlog.md`) routes F11/F12/F13 detail to. Sibling **deferred** features have their own notes: ambient scribe — `docs/f9-ambient-scribe.md`; AI inbox manager — `docs/f10-ai-inbox-manager.md`; follow-up tracker — `docs/f14-followup-tracker.md`. Parent / system design: `docs/ai-clinical-assistant-design.md`. Backlog index: `docs/feature-backlog.md`.
>
> All three features touch **real clinical workflows** (billing money, referrals between providers, legal/insurer paperwork) and are therefore **Phase 2/3** — each demonstrated on a **synthetic sandbox first**. **None of F11/F12/F13 is being implemented yet**; this doc is the design they are built to satisfy once the Phase-1 shared infra (capability registry, `/api/terminology`, `/api/audit` writer, `/api/fhir-write` broker, the de-id seam, and the per-feature scope union) actually lands.

## Shared architecture (how all three plug in)

All three features are **capability plug-ins** under the architecture in `docs/ai-clinical-assistant-design.md`. Each is a self-contained folder (`capabilities/<feature>/`) that exports **one descriptor** (id, name, FHIR scopes, tools, surface `chat|panel|proactive`, executionSide `client|server`, lifecycle hooks) plus **one `register(...)` line** in the barrel. The chat tools, system-prompt fragments, panel actions, proactive scanners, and requested OAuth scopes are **all derived at runtime from the registered descriptors** — shared infra never imports a feature.

> **Reality check (read first).** Per `docs/phase-1-todo.md`, the registry itself, `/api/terminology`, the `/api/audit` writer, the `/api/fhir-write` write loop, the de-id seam, and the per-feature scope union are **not built yet** — only `/api/chat` exists, tools are hardcoded in `lib/tools.ts`, and `lib/smart.ts` ships a blanket `patient/*.read` scope. So everywhere below that says "reuse," read it as **"reuse this shared route/pattern once it exists; each feature adds a new source / rule-pack / template / broker-segment behind it, not a new route class."** This is why all three are gated behind Phase-1 infra landing.

**Shared routes each feature uses:**
- **`/api/chat`** — the single server-side LLM gateway (Vercel AI SDK, default `claude-opus-4-8`); the provider key never reaches the browser. Used by all three only for *narration / prose framing / passage-ranking / intent mapping* — never to mint a code, fee, dose, date, or structured field. The **de-identification seam** runs here as the last step before LLM egress (permissive today; the target end-state per design §7).
- **`/api/terminology`** — the keyed external-knowledge route (RxNorm, DDI, ICD-10/SNOMED, guideline content, fee schedules). F11 adds the **fee-schedule corpus + code/fee lookup** behind it; F12/F13 touch it only if a destination/template requires a validated coded value.
- **`/api/fhir-write`** — the guarded write broker (privileged `*.write`, trusted validation, mandatory audit). F12/F13 reuse it directly for `ServiceRequest`/`DocumentReference`/`QuestionnaireResponse`/`Provenance`/`Task` write-back in Phase 2+. **F11 reuses the *pattern* but not the route** — its egress is a flat claim file to a payer over MCEDT/EDT, not a FHIR write-back, so it stands up a feature-owned privileged route.
- **`/api/audit`** — the append-only audit seam. Every draft / confirm / handoff / submit / code-edit is logged (who, patient, artifact, in/out, timestamp).

**Shared discipline — identical across all three:**
- **Never auto-write.** Everything follows **draft → explicit human confirm → submit**. The model proposes and narrates; the clinician confirms every code, field, attachment, signature, and submission. Nothing is auto-sent, auto-signed, or auto-submitted.
- **Deterministic-card principle.** Anything actionable or numeric (codes, fees, dates, attestation clauses, structured form fields) is **computed deterministically and rendered as a typed card**; the model never types one into free prose that bypasses the card.
- **Guardrails.** Every clinical claim / pre-filled field carries a **FHIR citation chip** resolving to a named source element ("no citation → no assertion"); every card shows an **"AI draft — review before use"** banner; writes/submissions route through the broker with audit.
- **De-id + audit on egress.** The de-id seam (last step before LLM egress in `/api/chat`) and the audit seam are on the call path, permissive in Phase 1. F11 carries an **explicit, governed exception**: its claim file *cannot* be de-identified (the payer needs real identifiers), so that egress is gated to Phase 3, BAA/residency-covered, and fully audited.
- **`synthetic|phi` phasing.** A central gate; Phase 1/2 run on the synthetic sandbox, real PHI is Phase 3.
- **Single-patient / in-context.** Unlike the deferred **F10 inbox** (which fans out across many patients), **F11, F12, and F13 are all single-patient, in-context** — exactly one in-context patient, no cross-patient scans. The one wrinkle is F11's **end-of-day batch register**, which aggregates the day's many patients *at the list level only* — the same invariant-moves-down-a-level tension F10 surfaces, and an explicit confirm item below.

## F11 — Billing & coding assistant

> Origin notes (2026-06-20): *"Billing cycle every 3 months"; "Learning how to bill"; "900 page billing"; "Missing code"; "Billing — EOD — diagnostic code + service code (az007) + blood work — sent batch file to ministry — back and forth."*

> **✅ Implemented — Phase-1 synthetic slice.** A deterministic builder ships now: `lib/billing.ts`
> (`buildBilling`) → the `suggest_billing_codes` tool + keyword route + `BillingCard` (typed card,
> tests in `lib/__tests__/billing.test.ts` + the card test). It proposes a service/fee line plus an
> OHIP-style 3-digit diagnostic line per charted problem (each cited to its `Condition`) and runs
> the **missing-code catch** (specimen-collection reminder when bloodwork is on file; a high-severity
> "no diagnostic code" flag). Codes/fees are a **curated SYNTHETIC subset**, labelled
> "confirm before billing"; VERA never submits. **Deferred to P2/3** (everything below this note):
> the real fee schedule + RAG, the ICD-10↔OHIP crosswalk, `Coverage`/`Claim` FHIR modeling, the EOD
> batch builder, the MCEDT/EDT submit broker, and rejection/remittance triage.

**The one-line pitch.** The clinician describes what they did; the assistant proposes the diagnostic + service + specimen-collection codes from the encounter, catches the ones they'd have missed, assembles the day's claims into the ministry's batch format for review, and — when the ministry bounces a claim — explains the rejection and proposes the fix. It turns a 900-page manual and a slow back-and-forth into a reviewed, one-click loop. **It drafts and proposes; the clinician confirms every code and every submission.** This is the highest-frequency, highest-friction item in the entire interview — every encounter, every day, plus a recurring reconciliation cycle.

### Pain (from the note)
Three distinct, compounding frictions, all named explicitly in the note:
1. **The 900-page fee schedule nobody memorizes.** "Learning how to bill" and "900 page billing" — the correct code for a given service is buried in a manual the clinician searches by hand, so they either guess, default to a familiar code, or tab out.
2. **Missed codes / under-billing.** "Missing code." Billable work done during the visit (a specimen drawn, a procedure performed, an add-on premium) never makes it onto the claim — silent lost revenue the clinician only discovers, if ever, at reconciliation.
3. **The end-of-day ministry round-trip.** "EOD — diagnostic code + service code (az007) + blood work — sent batch file to ministry — back and forth." Claims are batched at end of day, submitted to the payer, and a subset bounce back with error/reject codes later. Resolving each rejection means decoding a terse error, finding the right correction in the manual, re-coding, and resubmitting — the "back and forth" that the billing cycle is largely consumed by.

> The `az007` in the note is a **placeholder for the local service/fee-code shape**, not a verified real code. The actual code system, batch-file format, and rejection-code vocabulary all depend on the payer (see "Likely target" and Open questions). Whether the target is **OHIP** is the load-bearing unknown; *some* OHIP specifics below are documented facts *if* OHIP is the target. The `az007` token is illustrative only.

### The 10x bar
The EMR built-in is a code-lookup box plus a batch-export button: it makes you *find* the code and *type* it, and it tells you nothing about what you missed or why a claim bounced. The bar here is to move the clinician from **author** to **reviewer** end to end:

> From *"learn a 900-page manual, search it by hand, miss codes, batch blind, and eat a slow rejection back-and-forth"* → *"codes proposed from the encounter with the manual passage cited, missing/under-billing items caught before submit, the batch shown as a reviewable register, and every rejection explained in plain language with a corrected code one click away."*

Concretely 10x because it attacks all three frictions at once and closes the loop: (a) **suggestion** removes the manual search, (b) **missing-code catch** recovers revenue the built-in never surfaces, (c) **rejection triage** collapses a multi-day decode-and-resubmit cycle into a single reviewed action. The built-in does none of (b) or (c).

> **Dependency note (read first).** F11 is **not** a thin extension of already-built shared infra. Per `docs/phase-1-todo.md`, the routes it leans on do **not exist yet**: `/api/terminology` is an unbuilt P2 seam (§D), there is **no audit writer** today (§B), `/api/fhir-write` is only a seam (`draft_order` in `lib/tools.ts` just builds a card; the sign→write→submit loop is an open question, §D), and the **capability registry itself (§A) is not built** — tools are hardcoded in `lib/tools.ts`. Only `/api/chat` exists. So F11 is **gated on Phase-1 infra landing first**: the registry, the `/api/terminology` route, the `/api/audit` writer, and the `/api/fhir-write` broker pattern. Where this section says "reuse," read it as "reuse these shared routes *once they exist*; F11 adds a new **source / rule-pack / broker-segment** behind them, not new route classes."

### Build checklist
- [ ] **(1) Encounter → code suggestion (extends F7).** Given the in-context `Encounter` + its `Condition`s + `Procedure`s/`ServiceRequest`s + ordered `Observation`s/labs, deterministically resolve and propose: the **diagnostic code(s)**, the **service/fee code(s)** (the `az007`-shaped local code), and the **physician-billable specimen-collection code** (see the bloodwork caveat below). F7 already does ICD-10/SNOMED via `suggest_codes_and_guidance`; F11 adds the **local fee schedule** as a new terminology source behind the same route — but note the diagnostic vocabularies are **not the same system** (see the crosswalk caveat below). Each proposed code renders as a **selectable, cited row** in a typed **Billing-code card** — code + plain-language label + the fee-schedule passage it came from + the source FHIR resource (which `Condition`/`Procedure` justifies it). The model **never types a code or a fee into prose** (deterministic-card principle).
  - **Diagnostic-vocabulary caveat (not a clean F7 reuse).** If the target is **OHIP**, the claim's diagnostic code is drawn from OHIP's own **~3-digit "OHIP Diagnostic Code" set, which is ICD-9-derived** — a **different vocabulary** from F7's ICD-10/SNOMED. So F7's clinical codes do **not** map 1:1 onto the claim; F11 needs either a **crosswalk** (ICD-10/SNOMED → OHIP 3-digit) or a **separate diagnostic source**, not a direct reuse of F7's emitted codes. (The OHIP code-system *facts* are documented; whether OHIP is the target is the part that *needs confirmation*.)
  - **Bloodwork caveat (a common real-world mis-billing — and exactly the kind step (2) should catch).** In Ontario, **community/outpatient lab tests are billed to OHIP by the licensed laboratory** (Schedule of Benefits for Laboratory Services / L-codes), **not by the ordering physician** — the physician orders via a requisition and does **not** put a lab-assay fee code on their own claim. What the physician **can** bill is a **specimen-collection / venipuncture service fee (a G-code) when they personally collect the specimen** — not the assay. So "specimen/bloodwork code" on the physician's claim is realistic **only** for the collection fee. The assay-vs-collection distinction is a **confirm item**, and the assay-on-the-physician-claim error is precisely the kind of mis-billing the missing-code catch (2) should flag.

- [ ] **(2) Missing-code / under-billing catch.** A deterministic rule pass over (note + orders + the proposed claim) flags billable items present in the encounter but absent from the draft claim — e.g. "specimen personally collected (`Observation`/`ServiceRequest` present) but no specimen-collection G-code on the claim", "diagnostic code present but the paired service code missing." These are **internal advisory findings** carrying the F2/interactions **finding shape** (severity, triggering-resource refs, source/version tag) and ranking — they are **not** persisted as FHIR `DetectedIssue`/`Flag`, because those are **clinical-safety** resources, not billing-completeness ones; a billing gap is an app-internal advisory, not a clinical issue. **Fire/no-fire is always code, never the model** (same guarantee as the interactions logic).
  - **Premium flags are the highest-precision-required class.** OHIP premiums (after-hours / special-visit / sacrifice-of-office-hours, K-prefix, age/complexity premiums) are **highly rule-bound** (specific time windows, eligible base services, exclusivity rules that forbid combining certain premiums) and frequently **cannot be verified from FHIR alone** (e.g. whether office hours were genuinely sacrificed, or the exact time-of-service window). A confidently-fired premium that is actually ineligible is an **over-billing / audit-exposure error**, not just lost revenue. So premium rules must fire as **"possibly eligible — confirm against this premium's specific conditions (time window, eligible base service, exclusivity rules)"**, never as a clean assertion, and are flagged the highest-precision class in the rule pack. (Ties to the financial-error-liability open question.)

- [ ] **(3) End-of-day batch builder + review register.** Assemble the day's confirmed claims into the payer's **batch-file format** and present a **review register**: one row per claim. **Nothing is auto-submitted** — submission is an explicit human action through the broker (below) with the same draft → explicit-human-confirm → submit + **audit** gate.
  - **Register columns (OHIP granularity).** Per claim: patient, **Health Number + version code**, the clinician's own **accounting number** (the reference key the return reports key on for reconciliation — load-bearing for matching a rejection/RA line back to the original claim), service date, diagnostic code, **service code(s) with per-service "number of services" multiplier**, and fee total. Note the OHIP shape: an **account/claim header** groups **multiple service items** for one patient/encounter; the fee code, number of services, fee submitted, service date, and **diagnostic code attach at the service-item level**, while the **version code and HN attach at the patient/claim header level**.
  - **Transport vs. format (two distinct OHIP concepts — do not conflate).** *Needs confirmation that OHIP is the target*, but if so: **(a) the transport** is **MCEDT / EDT** (Medical Claims Electronic Data Transfer), the MOH's authenticated file-exchange channel/portal (web service + a **MOH-issued EDT account with conformance requirements / GoSecure auth** — *not* a generic API-key secret); **(b) the file format** is the separate **MOH Claims File** specification (legacy fixed-width record types — header / service records), distinct from the channel. So the artifact is "**a MOH Claims File (fixed-width batch) sent over MCEDT/EDT**," not a single "MOH EDT file."

- [ ] **(4) Rejection / remittance triage (closes the back-and-forth).** Ingest the returned files, parse each rejected/adjusted claim (matched on the **accounting number**), and render a triage card: the original claim, the **rejection/error code decoded into plain language**, the likely cause, and a **proposed corrected code** (re-running suggestion (1) with the rejection reason as a constraint). One-click "accept correction" stages the claim for the next batch — **never auto-resubmits**. This is the single highest-leverage piece.
  - **There are (at least) three distinct OHIP return artifacts, on different cadences** — a single "remittance" mapping flattens them:
    1. the **EDT batch-edit / file-reject report** (returned shortly after upload — rejects malformed claims/records *before* adjudication);
    2. the **Claims Error Report** (claims that failed adjudication edits, with EC0x-style error codes, returned on the **monthly** cycle);
    3. the **Remittance Advice (RA / RA Inquiry)** — the paid/adjusted statement issued on the **monthly** OHIP payment cycle (mid-month).
  - **Cadence correction.** OHIP's payment/RA cycle is **monthly**, with a **~mid-month (≈18th) fee-submission cutoff** and a **~6-month stale-dating limit** (older claims refused). The note's **"every 3 months"** is plausibly the **clinician's own reconciliation habit**, **not** the ministry cadence — do not present quarterly as OHIP's cycle.

- [ ] **(5) Fee-schedule RAG over the 900-page manual.** Index the fee-schedule manual so "how do I bill X?" / "what's the code for an after-hours specimen collection?" is answerable inline, **with the passage cited**. Served through **`/api/terminology`** (once built — see Dependency note) so it shares the keyed-source, CORS-restricted, server-key plumbing. RAG retrieves and grounds; the **deterministic terminology lookup**, not the model, emits the actual code/fee — the model can rank and explain passages but cannot invent or alter a code or a fee.
- [ ] **Guardrails throughout.** Every proposed code carries its fee-schedule citation + its source FHIR resource; every card shows an **"AI draft — review before billing"** banner; fees and codes are deterministic and shown for confirmation, never narrated; the submit and the re-code are both explicit, audited human actions.

### FHIR mapping (read / write + phase)
- **Read (Phase 2 on synthetic, Phase 3 on PHI):** `Encounter` (the visit being billed), `Condition` (→ diagnostic code), `Procedure` and `ServiceRequest` (→ service/procedure codes), `Observation` / `DiagnosticReport` (→ specimen-collection justification), `Patient` (**demographics only**), **`Coverage`** (the payer/policy — see below), `Practitioner`/`PractitionerRole` (the billing provider + billing number — see below). All *patient-compartment* reads are single-patient, in-context, on the existing patient-scoped token; the provider resources are **not** patient-compartment (see scopes below).
- **`Coverage` is required, not optional.** R4 `Claim.insurance` is cardinality **1..\*** and each entry references a **`Coverage`** resource — so the payer/health-card identifier lives on **`Coverage`, not `Patient`**: `Coverage.payor` (the ministry / `Organization`), `Coverage.subscriberId` / `Coverage.identifier` (the **Health Number**; for OHIP the **version code** also rides here / on `Patient`), `Coverage.beneficiary` → `Patient`. `Claim.insurance[0].coverage` references it and is **mandatory** — without `Coverage` in the read/build set, **no conformant `Claim` can be assembled**. Keep `Patient` for demographics only.
- **Billing artifact (write) — corrected R4 model.** The draft claim is a **`Claim` (status `draft`)** whose **line items are `Claim.item` entries** — **not** "composed of `ChargeItem`s." In R4 there is **no `Claim.chargeItem` element and `Claim` never references `ChargeItem`**; the two never compose. Each billable line maps as:
  - `Claim.item.productOrService` = the **service/fee code**;
  - `Claim.item.net` = the **fee**;
  - `Claim.item.diagnosisSequence` → `Claim.diagnosis[*].diagnosisCodeableConcept` (or `.diagnosisReference` → `Condition`) = the **diagnostic code**;
  - `Claim.item.encounter` → the `Encounter`;
  - `Claim.supportingInfo` → the `Procedure` / `Observation` / `DiagnosticReport` evidence;
  - `Claim.provider` → the billing `Practitioner` / `PractitionerRole`.
  - **`ChargeItem` (optional, useful for step (2)).** If a discrete *pre-claim* billable-event record is kept, `ChargeItem` is the **source of truth that *feeds* `Claim.item` population** — recording that a billable event occurred — **not a child the `Claim` is composed of**. In R4, `ChargeItem` is aggregated by `Account` / `Invoice`, never assembled into a `Claim`. Its own linkage is via `ChargeItem.context` (→ `Encounter`) and `ChargeItem.service` (→ `Procedure`/`ServiceRequest`). The whole `Claim` / `ChargeItem` / `Invoice` modeling is **needs-confirmation against the chosen payer**, the same way the remittance mapping is.
- **Citation-chip bindings (the deterministic-card depends on these).** Each evidence chip resolves to a **named FHIR element**, not free text: diagnostic chip → `Claim.diagnosis.diagnosisReference` (→ `Condition`); encounter chip → `Claim.item.encounter`; procedure/lab chips → `Claim.supportingInfo` (→ `Procedure`/`Observation`/`DiagnosticReport`); billing-provider chip → `Claim.provider`.
- **Billing number is a deterministic identifier, not free text.** The provider's billing/OHIP number is an **`identifier`** — preferably **`PractitionerRole.identifier`** (the role/clinic-scoped billing number, with **specialty/group code** and **service-location/facility number** alongside), falling back to **`Practitioner.identifier`**. On the built claim it surfaces as **`Claim.provider`** (reference) plus that identifier. The card **resolves** it from the resource; the model **never types** it (deterministic-card principle). For OHIP the claim's mandatory identifier set is, concretely: **Health Number + version code** (from `Patient`/`Coverage`), **billing number + 4-digit specialty/group code + service-location/facility number** (from `Practitioner`/`PractitionerRole`).
- **Remittance — three artifacts, one loose internal analogue.** `ClaimResponse` is the correct R4 target for the **adjudication result only**, and it **cannot cleanly carry all three OHIP return artifacts** (file/batch-edit reject report, monthly Error Report, monthly Remittance Advice — see Build (4)). Within R4, the triage card projects: **`ClaimResponse.outcome`** (`queued|complete|error|partial`) as the status it keys off, **`ClaimResponse.error.code`** (decoded to plain language) for the rejection reason, and **`ClaimResponse.item.adjudication`** for adjusted/paid detail. The **external flat-file parse stays in the broker**; `ClaimResponse` is a loose internal analogue and **explicitly does not represent the RA or the file-reject report**. *The real return is a proprietary flat file, not FHIR — needs confirmation.*
- **Ministry submission is NOT raw FHIR.** The batch file sent to the payer and the return files are **external, payer-specific formats** (for OHIP: a **MOH Claims File** over **MCEDT/EDT** — *needs confirmation*), produced and parsed by a **submit broker**, not by writing FHIR to an EHR endpoint. FHIR is the internal representation; the broker is the egress/ingress seam to the ministry.
- **Phase.** **Phase 2 (build + demo on synthetic claims)** and **Phase 3 (real claims to a real payer)**. Real claims are **money + PHI + an irreversible external submission**, so they require the audit log, a guarded submit broker, and write-scope/financial governance — none of which are Phase-1 surfaces. The **suggestion + missing-catch + RAG** sub-features ((1),(2),(5)) are demonstrable on synthetic encounters earlier and are the lowest-risk slice; the **batch builder + submit + rejection triage** ((3),(4)) are gated to the broker and to PHI.

### Client vs. server split
- **Client (browser, patient-scoped token):** read the in-context `Encounter`/`Condition`/`Procedure`/`Observation`/`Coverage` via the existing Data Access layer; render the Billing-code card, the missing-code flags, the EOD review register, and the rejection-triage cards; capture the clinician's confirm/edit/reject and code selections; resolve citation chips back to the named source FHIR element and to the fee-schedule passage. Cheap deterministic local checks (e.g. "diagnostic code chosen but no service code") can run client-side for instant feedback, mirroring the F2/interactions pattern.
- **Declared FHIR scopes (enumerated — least-privilege).** F11 needs read scopes **no existing capability declares** (F7, the parent, declares only `patient/Condition.read` + `patient/MedicationRequest.read`). The descriptor must explicitly declare: `patient/Encounter.read`, `patient/Procedure.read`, `patient/ServiceRequest.read`, `patient/Observation.read`, `patient/DiagnosticReport.read`, **`patient/Coverage.read`**. `Practitioner`/`PractitionerRole` are **outside the patient compartment**, so `patient/*` scoping may not grant them — they need **`user/Practitioner.read`** / **`user/PractitionerRole.read`** (or resolution from the launch / `fhirUser` context). The financial **`patient/Claim.write`** (Phase 2 synthetic / Phase 3 real) is declared **separately and gated to the broker**, mirroring how F5's `patient/MedicationRequest.write` is gated.
- **Server (`/api/*` route handlers):**
  - **`/api/terminology`** (once built) — fee-schedule RAG + the authoritative **code/fee lookup**; holds the manual index and any keyed payer-code source; the only place a code/fee is minted (browser can't bypass it). Shared with F2/F7 *once that route exists*.
  - **`/api/chat`** — the LLM gateway for narration, RAG-passage ranking, plain-language rejection explanation, and intent→code-search-query mapping; runs the **de-identification seam** before egress. The model sees the question/note text and minimized context, never mints a code.
  - **Submit broker — NEW feature-owned privileged route (e.g. `/api/claim-submit`), not `/api/fhir-write`.** Be explicit: F11 does **not** reuse `/api/fhir-write` itself — that broker writes **FHIR to an EHR**, whereas this **transmits a flat file to a payer over MCEDT/EDT**. F11 stands up a **new, feature-owned privileged egress route** that **copies the draft→confirm→submit+audit *pattern*** (and is **needs-server** for the same three reasons F5 is: privileged write, trusted validation, mandatory audit). It must still route through **`/api/audit`** and respect the de-id policy below. This is genuinely **new bespoke privileged infra**, not pattern-only reuse — the design does not get to have it both ways.
- **De-id seam on the broker egress (the highest-PHI path).** The §7 de-id seam lives in `/api/chat` as the last step before *LLM* egress — but F11's **highest-PHI egress is the claim batch file leaving the submit broker to the ministry**, which by necessity carries **name, Health Number, DOB, and billing identifiers**, and does **not** pass through `/api/chat`. The claim file **cannot be de-identified** (the payer needs the real identifiers to adjudicate and pay). State this as an **intentional, governed exception** to the de-id seam: **gated to Phase 3, BAA / data-residency-covered, and audited with full payload-reference logging** — rather than letting the reader assume the §7 seam covers it.
- **Why this split:** payer credentials, the fee-schedule corpus, the LLM key, and the audit trail are all secrets/trusted-context concerns; FHIR reads of the in-context patient are already authorized in the browser. Same asymmetry as the rest of the app (§5).

### How it reuses existing infra
*(See the Dependency note — most of these are seams/TODO per `docs/phase-1-todo.md`, not yet built. "Reuse" = "reuse once built; F11 adds a source/rule-pack/broker-segment behind them, not new route classes.")*
- **F7 (guideline & coding lookup)** — F11 extends F7 from clinical terminology (ICD-10/SNOMED) into the **local fee schedule**: same deterministic-code discipline, same cited-selectable-row UX, same `/api/terminology` dependency. **But not a clean reuse of F7's codes** — the OHIP diagnostic vocabulary is a different (ICD-9-derived 3-digit) system requiring a crosswalk or separate source (see Build (1)). F7's `suggest_codes_and_guidance` is the sibling tool.
- **`/api/terminology`** (the shared keyed-knowledge route, **to be built** — P2 seam per §D) — would host the fee-schedule RAG corpus and the code/fee lookup. No new route class; a new *source* behind the existing one **once it exists**.
- **Deterministic versioned-rule-pack discipline (the F2/interactions pattern)** — F11's missing-code/under-billing catch **mirrors the shape**: a versioned rule pack, deterministic fire/no-fire, severity ranking, triggering-resource refs, a source/version tag (cf. `lib/interactions.ts`, `source: 'curated-ddi@2025.1'`). **Honest caveat:** there is **no extracted, shared rule-engine module** today — the logic lives as plain functions/arrays in `lib/tools.ts` (`buildReconcile`) and `lib/interactions.ts` (`RULES`), and F8's on-load scanner is **not implemented**. So this is a **discipline/shape, not a pluggable engine**. F11 either ships its **own self-contained billing rule pack inside `capabilities/billing-coding/`** (consistent with removability) **or** a shared rule-engine abstraction must first be **factored out**.

> **Origin notes (clinician):**
> - *"Referrals"*
> - *"Notes for specialists, in this specific form. Ocean portal. EMT"*
> - *"E-referrals standardizing"*

A capability that turns the in-context chart into a **destination-specific, pre-filled, cited referral package** — a referral letter plus the structured `ServiceRequest` and its attachments — that the clinician reviews, completes, and **hands off** to the receiving system's portal. The assistant assembles and pre-fills; it never auto-sends. We generate the payload; we do **not** build transport.

### Pain

Each specialist service and intake pathway wants a *different* referral form. The clinician re-keys the same patient data — demographics, problem list, current meds, allergies, recent labs/imaging, reason for referral — into portal-specific templates, once per destination, by hand. The data already exists, structured, in the chart they're looking at; the work is pure transcription into someone else's field layout, plus hunting down and attaching the right supporting documents (recent labs, the imaging report, a standalone "ACP and DNR Status" document). Every destination re-introduces the same copy-paste-and-attach toil and the same chance of a missed required field that bounces the referral back.

> **10x bar:** The EMR built-in (and the receiving portal itself — *needs confirmation* this is Ocean eReferral / OceanMD; see Open questions) presents an **empty** destination form and makes the clinician fill it. The 10x version presents the *same destination form already filled from the chart, every field cited to its source resource, with the missing-required fields flagged before they hit "send" and the right attachments pre-selected* — so the clinician's job collapses from "re-key and assemble" to "review, complete the few chart-can't-fill fields, and hand off." Target: from a blank form to a review-and-confirm step. (Note: if the target is Ocean, the actual handoff is via Ocean's own EMR integration / Ocean Online, **not** a generic field-params deep-link — see Build step 6 and Open questions.)

### Build (checklist)

1. **Per-destination template registry.** A versioned, declarative catalog of referral destinations (e.g. *Cardiology — Ocean eReferral form X*; *needs confirmation* on which specialties/forms are in scope — see Open questions). Each template declares: required fields, optional fields, required attachment *types* (e.g. "recent ECG", "ACP/DNR status"), the **field → chart-source mapping** (which FHIR resource/path fills each field), and the **attachment-linkage path** (how this destination expects supporting documents to be attached — see step 5). The template is data, not code, so adding a destination is adding a template, not editing the capability. **Do not author the registry against Ocean-specific forms until region+portal are confirmed:** build the mapper and completeness-check against a synthetic, portal-agnostic destination template first, so a region change (e.g. a non-Ontario target) does not invalidate the engine.
2. **Deterministic pre-fill (the chart → form mapper).** For a chosen destination, walk the template's field map and pull values from the chart slices: Patient demographics, active Conditions (reason for referral + relevant history), MedicationRequest list, AllergyIntolerance, recent Observations, and any relevant DocumentReference attachments. **Every pre-filled field carries a citation** to its source resource (reusing F1's citation chips). The mapper is deterministic — the model never types a value into a form field. *Note (see Reuse):* Patient/Condition/MedicationRequest/laboratory-Observation come from the already-cached slices, but AllergyIntolerance, DiagnosticReport, and DocumentReference are **not** fetched anywhere today and require **new fetchers** added to the shared Data Access layer.
3. **Completeness check (the gate).** Before any handoff, compute and surface: required fields the chart **cannot** fill (rendered as `[clinician to complete]`, never guessed), required attachment types that are **missing** from the chart, and fields filled from **stale** data (e.g. labs older than the destination's recency window — *needs confirmation* on whether destinations specify recency). This is the deterministic-card analog of F2's "coverage gaps" — it distinguishes "filled," "you must complete," and "we couldn't find this" rather than implying a complete package.
4. **Editable, cited referral letter + structured request.** Render a **typed Referral card**: (a) a prose referral letter generated from the chart and the chosen template's framing — editable, each clinical claim cited; (b) the structured field table mapping to first-class `ServiceRequest` elements (see FHIR mapping); (c) the attachment list (the supporting `DocumentReference`/`Observation`/`DiagnosticReport` resources), each with an include/exclude toggle. Banner: *"AI-drafted referral — review and complete before sending. Not sent."* The LLM writes the letter prose and chooses the destination/specialty intent; it never sets a code, dose, or required structured field — those come from the deterministic mapper. *Document-Bundle note:* in Phase 1 the letter is narrative / a future `DocumentReference`; **if** a transport requiring a FHIR *document* Bundle is later selected (e.g. an XDS-published CDA path for a non-Ocean receiver), the letter's structured analog is a `Composition` (type = *referral note*) forming the first entry of that document Bundle — *needs confirmation*, flagged alongside the transport open question.
5. **Attachment selection.** From the chart's DocumentReferences and recent Observations/DiagnosticReports, deterministically propose the attachments the template requires (recent labs, imaging report, the standalone "ACP and DNR Status" clinical document — *likely a PDF (`application/pdf`) / scanned binary carried in `DocumentReference.content.attachment`; possibly HL7 CDA if sourced from a structured ACP module; format unconfirmed*). The clinician confirms/toggles each. A standalone clinical document (ACP/DNR) is treated as an **attachment**, **not** as the referral request itself. **Attachment-linkage caveat:** modeling attachments via `ServiceRequest.supportingInfo` is the default here, but the exact linkage (`ServiceRequest.supportingInfo` vs. a Bundle-level `DocumentReference`/`Communication` vs. a profile-specific extension) **depends on the confirmed destination/referral profile** (Ocean eReferral, or a CA-Core / US-Core `ServiceRequest` profile) — `supportingInfo` is a `Reference(Any)` whose semantics vary by implementer. The mapper therefore treats the attachment-linkage path as **template-declared data**, not a hard-coded assumption (listed alongside the "envelope shape" open question).
6. **Export / handoff seam (the integration boundary).** On explicit clinician confirm, assemble the **envelope** — a FHIR `Bundle` (`type=collection` for a self-contained handoff export; or `type=transaction` if it is later POSTed to a FHIR receiver as an atomic create) containing the `ServiceRequest` + referenced supporting resources — and hand it off. It is **not** a FHIR *document* Bundle (no `Composition`) unless/until a transport that requires one is chosen (see step 4). Phase 1: **export only** — a downloadable/copyable Bundle plus the printable letter. **We do not build transport.** Critically, separate *what envelope F12 generates* from *how a given destination ingests it*: **if** the target is Ocean (*needs confirmation*), the realistic Phase-1 handoff is Ocean's own integration (its EMR plug-in / Ocean Online pre-fill / Ocean cloud routing: sender EMR → Ocean cloud → receiving site's Ocean inbox), **not** a generic field-params deep-link and **not** IHE XDS.b / XDR / Direct secure messaging (those are US/cross-jurisdiction HIE patterns used by *other*, non-Ocean receivers we do not target in Phase 1). F12 produces the payload and stops at the seam; real submission flows through the guarded write broker in a later phase (see FHIR mapping).
7. **Tracking handle (consumed downstream).** On the **same explicit "confirm handoff" click** that produces the export, create a `Task` to track the referral to closure. In Phase 1 this Task is an **in-memory / local export artifact only** — part of the exported Bundle or a local worklist entry. It is **not persisted** anywhere, carries **no patient-identified write**, and is created solely as a side effect of that confirm action — **logged through `/api/audit`** like the handoff event itself (so it is gated and audited, not a silent external effect). Element mapping: `Task.focus → ServiceRequest` (the thing acted upon), `Task.for → Patient`, `Task.code = fulfill`, `Task.intent = order`, `Task.status = draft`/`requested` (local in P1). Any **server write of the Task** is deferred to Phase 2 through `/api/fhir-write`, matching the ServiceRequest. The deferred **F14 follow-up tracker** (see `docs/f14-followup-tracker.md` — a deferred Phase-2 note that names F12 as its upstream `ServiceRequest` + `Task` producer and is itself single-patient/in-context) consumes this Task via `Task.focus`/`Task.for`.

### Client-vs-server split

- **Client (browser, patient-scoped read token):** fetch the chart slices (through the shared Data Access layer — reusing the cached Patient/Condition/MedicationRequest/Observation slices and the **new** AllergyIntolerance/DiagnosticReport/DocumentReference fetchers added there), run the **deterministic field-map pre-fill**, run the **completeness check**, render the editable Referral card and attachment toggles, resolve citations, and (Phase 1) assemble + download/copy the export Bundle and create the local tracking Task. All read-only; no secret needed.
- **Server (`/api/chat` only, Phase 1):** the LLM writes the **referral-letter prose** and chooses the destination intent — through the one gateway. The design's intent is that this call go over a **de-identified, minimized** bundle via the central de-id egress seam. **Be honest about current state:** that seam is **not yet implemented** — `app/api/chat/route.ts` today `JSON.stringify`s the full `patientContext` (including name, dob, mrn) straight into the system prompt. So the de-id/minimization is the **Phase-1 seam on the call path (permissive today, per the design doc)**, the target end-state, not a property F12 can rely on now. **No** structured field value, code, or attachment decision originates server-side regardless.
- **Server (later phases):** `/api/fhir-write` brokers the `ServiceRequest`/`DocumentReference`/`Task` write-back and (if/when we go past export) any real submission, enforcing draft → explicit human confirm → submit + audit. `/api/audit` logs every draft/confirm/handoff (including the Phase-1 local-Task creation).

The split mirrors the existing rule: **FHIR reads + deterministic assembly stay in the browser; the LLM call and any write/submit are server-side.**

A template-driven document generator: the clinician picks a form (sick note, return-to-work, a disability/insurer attestation, generic letter), the assistant prefills it from the in-context chart, the clinician edits and signs, and the output is a clean, printable/exportable document. It is the **paperwork sibling of F3 (plain-language summary) and F6 (note assistant)** — the same generate → cite → review-before-use → never-auto-issue spine, pointed at a *structured template* instead of free prose. The deterministic-card principle applies verbatim: the **template is the typed card**; the model narrates and frames but never types a date, a code, or an attestation clause into free prose that bypasses the form.

### Pain

A long tail of one-off documents — sick/work notes, return-to-work letters, disability/insurer forms, generic attestations — each drafted from a blank page. The clinical facts already live in the chart (active problems, the encounter date, the patient's identifiers), but the clinician re-keys them by hand into prose every time, formats it, and prints it. Individually each form is small; in aggregate it is a constant, low-value documentation tax with no leverage, and the EMR's built-in "letter" feature is usually a bare rich-text box with a mail-merge of the patient header and nothing else.

*(Domain caveat — needs confirmation: a meaningful slice of the plain "sick note" demand may be legislated away in the probable target. Under Ontario's Working for Workers amendments — understood to be in force since Oct 2024, **needs confirmation** — employers are reportedly barred from requiring an ESA sick note for the up-to-3 job-protected unpaid sick days. If so, the surviving demand is exactly the harder cases — absences beyond ESA days, and employer/insurer-specific formats — where a generic free-text note is weakest. This sharpens, rather than removes, the case for F13, but it is an open question whether the target clinic still needs a plain sick-note template at all; see Open questions.)*

### Build checklist

- [ ] **Template library (the core asset).** A registry of form/letter templates, each a typed schema — `id`, display name, ordered list of fields with `{key, label, type, source}`, a body/layout, and a `requiredScopes`/`requiredResources` declaration. Seed set: **sick / work-absence note**, **return-to-work / fitness-to-work letter**, a **disability/insurer attestation** (which specific form is an open question — see below), and **generic clinical attestation/letter**. Templates are data, not code, so adding one is adding a file — not editing the feature.
- [ ] **Template picker UI.** A "Generate a form/letter" affordance in the shared dock (and a panel action) that lists templates from the registry. Picking one opens the draft card.
- [ ] **Deterministic prefill.** For each template field with a chart `source`, pull the value from the Data Access cache (patient demographics, the in-context Encounter date, active Conditions) and fill it. Fields with no chart source render as **empty, explicitly-labelled blanks** for the clinician (e.g. work-restriction dates, "fit / unfit" determination, the functional limitations or clinical opinion an attestation requires) — the assistant must not invent a return-to-work date or a disability determination.
- [ ] **LLM framing only.** The model phrases the prose connective tissue (a courteous letter body, a plain-language reason-for-absence sentence) **over the prefilled fields**, never authoring a new clinical fact, date, code, or determination. A post-generation verbatim check confirms every patient identifier / date / condition in the output matches the prefilled field set (same guard as F3/F6).
- [ ] **Citation chips per field.** Each chart-derived field carries a source chip (`[Encounter · 2026-06-18]`, `[Condition · Major depressive disorder]`) deep-linking to the resource, exactly like F1/F3.
- [ ] **Completeness check.** Before "ready to sign," flag any required field the chart could not fill — *"return-to-work date not set," "no active Condition selected for this attestation"* — so the clinician is never handed a silently-incomplete form (the same gap-checklist idea as F6's "sources considered" list). *(F12 e-referrals shares the same template-fill-complete-check shape — a generic completeness primitive is the natural thing to factor across F12/F13; see "How it reuses existing infra.")*
- [ ] **Edit → sign → issue, never auto-issue.** Every field is inline-editable. A persistent **"AI draft — review before use"** banner and a "not yet signed / not issued" status. The clinician signs; only then does the document become final. Phase 1 stops at **export/print** (copy, download PDF/print) — no chart write-back.
- [ ] **Clean printable/exportable output.** Render the signed document to a print stylesheet and an exportable file (PDF/print-to-PDF), with the clinic letterhead/practitioner block and signature line. This is a real deliverable the patient walks out with — the output fidelity *is* the feature.
- [ ] **Minimum-necessary, per template (not a blanket "no diagnosis").** A **plain sick/absence note** should disclose an absence and dates, **not** the underlying diagnosis — that's the privacy default for that template specifically. But this does **not** generalize: **return-to-work / functional-abilities, disability, and insurer/LTD templates routinely and lawfully carry more** — functional limitations and sometimes the diagnosis — typically with patient consent. So each template's field set is an allow-list, and the *sensitive fields are opt-in per template*: off by default on the plain sick note, deliberately on (consent-gated) for RTW/disability/insurer forms. This is a privacy property enforced by template construction, not a layout one. *(Needs confirmation: exactly how much clinical detail each note type is permitted/expected to carry — jurisdiction-, employer-, and insurer-dependent.)*

### FHIR mapping (read / write + phase)

- **Read (Phase 1):**
  - **Patient-compartment (patient-scoped SMART read):** `Patient` (name, DOB/age, identifiers for the header), `Encounter` (the visit the note attests to — date, type), `Condition` (active problem(s) a fitness/disability form references), `Observation` optionally where a template cites a result. These are expressible as `patient/<Resource>.read`.
  - **Letterhead / signing block (NOT patient-compartment):** `Practitioner` / `PractitionerRole` / `Organization`. These are **not in the FHIR R4 patient compartment**, so they cannot be requested as `patient/*.read` scopes. The signing clinician + clinic block come from one of: the SMART **launch context / `fhirUser` + id token** (often enough to identify the practitioner with no extra read scope at all), a **`user/Practitioner.read` / `user/PractitionerRole.read` / `user/Organization.read`** scope, or **static clinic config**. Prefer launch-context/config so F13 adds no patient-scoped read for letterhead.
- **Write (Phase 2+) — this section's own proposal (the backlog index does not enumerate F13's write resources):**
  - **`DocumentReference`** for the issued document. **The not-yet-signed state lives on `docStatus`, not `status`:** `DocumentReference.docStatus=preliminary` while unsigned → `docStatus=final` once the clinician signs, with **`DocumentReference.status=current` throughout** (`status` is bound to `document-reference-status` = `current | superseded | entered-in-error` and reflects the reference's *relevance*, not the document's authoring state). **Note:** `preliminary` is a `Composition.status` / `DiagnosticReport.status` code — it is **not** valid on `DocumentReference.status`; putting it there would be rejected by a conformant server. `type` = the letter kind (see code caveat below); `context.encounter` links the visit.
  - **`Provenance`** (added, consistent with F6) — `Provenance.target` → the `DocumentReference`/`QuestionnaireResponse`, `Provenance.agent.who` = the signing `Practitioner`, asserting **human authorship/attestation** and recording the explicit human-confirm event. This is the FHIR artifact that *backs the "never AI-signed" guarantee* on F13's own write; without it the property has no resource backing. (If a structured form is also AI-assisted, a second `agent` can record the AI-assist role distinct from the human signer.)
  - **`QuestionnaireResponse`** for structured questionnaire-shaped forms (e.g. a disability form rendered as a `Questionnaire`). **Its lifecycle is its own, and also does not use `preliminary`:** `QuestionnaireResponse.status=in-progress` while filling/editing → `status=completed` once the clinician finalizes (`QR.status` = `in-progress | completed | amended | entered-in-error | stopped`).
  - **`DocumentReference.type` coding caveat — needs confirmation:** typing via LOINC/SNOMED is best-effort; "sick note," "return-to-work letter," and especially a CRA-DTC export **do not have crisp, universally-used document-type codes**. Use a best-effort code per letter kind and flag the exact value as needing confirmation — several have no canonical code.
  - All writes go through the guarded broker, draft → explicit human confirm → submit, never AI-signed (mirrors F6's `DocumentReference` + `Provenance` write).
- **Phase:** the generator is a **Phase 1** draft-and-print capability on synthetic data (everything except write-back can ship now); `DocumentReference` / `QuestionnaireResponse` / `Provenance` **write-back is Phase 2**.

*Needs confirmation:* whether the disability/insurer form maps cleanly to a FHIR `Questionnaire`/`QuestionnaireResponse` at all, or is an **opaque agency/insurer PDF** the app only *prefills and exports* (no structured FHIR write). Most likely the latter for Phase 1 — flag it.

### Client-vs-server split

- **Client (browser, patient-scoped token):** template picker, the deterministic prefill from the Data Access cache, the editable draft card, field-level citation resolution, the completeness check, and the print/export rendering. All of this is "read FHIR + render," so it stays client-side — no new disclosure beyond what the clinician is already authorized to see.
- **Server (`/api/chat`):** only the LLM call that frames the prose, behind **the de-identification and audit seams the architecture mandates on `/api/chat`**. To be honest about current state: these seams are **Phase-1 items to be built and exercised permissively on synthetic data — they are not yet shipped middleware** (today `/api/chat` posts the patient context straight into the system prompt with no redaction and makes no `/api/audit` call; see design §5/§7/§8). Because F13 sends a chart slice to the model exactly like F1/F3/F6, **F13 cannot ship until the de-id/audit seam is actually on the `/api/chat` path.** The provider key never reaches the browser. Like F3/F6, F13 is **hybrid, effectively server** — its only privileged work is the one model call; if the model is unavailable, the template still prefills and prints deterministically with template-default wording (graceful degradation).
- **Server (`/api/fhir-write`, Phase 2):** the guarded write broker holds `*.write`, enforces draft → confirm → submit, and audits the `DocumentReference`/`QuestionnaireResponse`/`Provenance` write. The client is never trusted to author the write.

### How it reuses existing infra

- **Shared route `/api/chat`** — the one LLM gateway (Vercel AI SDK, default `claude-opus-4-8`); F13 contributes a tool/prompt fragment and consumes the same (to-be-built) de-id + audit middleware on the path. No new LLM route.
- **Shared route `/api/fhir-write`** (Phase 2) — the same guarded write broker F5 owns and F6 reuses; F13 reuses it for the `DocumentReference`/`QuestionnaireResponse`/`Provenance` write rather than minting its own write path.
- **F3 (plain-language summary)** — reuses the facts-table + verbatim-post-check generation pattern and the "AI-generated draft — review before use" banner; F13 is the same generator pointed at a fixed template.
- **F6 (note assistant)** — reuses the `DocumentReference` + `Provenance` (`docStatus=preliminary` → `final`), never-AI-signed write-back model and the "sources considered / gap checklist" completeness idea. *(Note: F6's own mapping in §F6 currently states `status=preliminary` on `DocumentReference`, which is the same invalid-code defect fixed here — that parallel claim should be corrected to `docStatus` so the bug does not propagate.)*
- **F1 (grounded Q&A)** — reuses the citation-chip + deep-link-to-resource infra for per-field provenance.
- **F12 (e-referrals, this same doc)** — a near-twin in shape: both are "fill a destination-specific template from the chart, complete-check, review, export, never auto-send." Because F12 and F13 are now specced together here, the two **should share a generic completeness/template-rendering primitive**, and a shared "document generator" core becomes worth considering (Open question below) — versus keeping them two independent, separately-removable capabilities (the cleaner-removability default).

### Removability

Delete `capabilities/forms-letters/` and its one `register(...)` line in the barrel. What disappears: the "Generate a form/letter" dock affordance and panel action, the template-picker and draft card, the template library, and (Phase 2) F13's slice of the `/api/fhir-write` call for `DocumentReference`/`QuestionnaireResponse`/`Provenance`. The OAuth scope set narrows accordingly — F13's **patient-compartment** read (`patient/Encounter.read`, if no other capability declares it) drops from the patient-scope union, and any **user-level** letterhead scopes (`user/Practitioner.read`, `user/PractitionerRole.read`, `user/Organization.read`) drop from the *user-scope* set, not the patient-scope union (these resources aren't patient-compartment); the Phase-2 `DocumentReference.write` scope drops if no other feature declares it. Nothing in F1–F8/F9–F14 reads F13's output, and shared infra names no feature, so the build stays green. Adding it back is the mirror image: drop the folder, add one `register` line, declare scopes/resources/tools, edit no shared file. Individual templates are sub-removable — deleting a template file removes just that form, leaving the capability intact.

*Implementation-honesty note:* this removability/scope-narrowing story is **design-accurate, not yet implementation-true**. The current codebase has no `capabilities/` directory, no registry barrel, no boundary lint rule, and SMART scope is still the blanket `patient/*.read` (`lib/smart.ts`) — so there is no per-capability scope union to narrow *yet*. The registry, the union-of-scopes derivation, and the boundary lint rule are unbuilt Phase-1 items (tracked in design §3/§8/§9). The prose above describes the contract F13 is built to satisfy once that machinery exists.

### The 10x bar

From **"write each note from a blank page — re-key the patient header, the dates, the reason, format it, print it"** → **"pick the form, confirm the prefilled details, sign."** The EMR built-in is, at best, a letterhead mail-merge into a free-text box; F13's 10x is (1) the **clinical facts already filled and cited** from the chart, (2) a **completeness check** so an incomplete form can't be silently handed out, (3) **minimum-necessary disclosure by template construction** (a plain sick note that doesn't leak the diagnosis; RTW/disability/insurer forms carrying the consent-gated detail they actually require), and (4) a **clean export** the patient can use. The target is editing-and-signing, not authoring. If a template only saves the letterhead keystrokes, it has not cleared the bar and should not ship — and, per the domain caveat above, the **plain sick note may be the weakest candidate** (legislated-away ESA demand, and the EMR mail-merge already does much of it); the value concentrates in the **RTW / disability / insurer** forms where chart-grounded prefill + completeness + consent-gated disclosure actually save real work.

## Cross-cutting

**Reuse map — how F11/F12/F13 sit relative to the built features F1–F8.**

- **F11 extends F7.** F11 is the billing/financial extension of F7's guideline-and-coding lookup: same deterministic-code discipline, same cited-selectable-row UX, same `/api/terminology` dependency — but pointed at the **local fee schedule** rather than ICD-10/SNOMED, with the load-bearing caveat that the OHIP diagnostic vocabulary is a *different* (ICD-9-derived 3-digit) system needing a crosswalk or separate source, not a clean reuse of F7's emitted codes. F11's missing-code rule pack also mirrors the **F2/interactions versioned-rule-pack shape** (deterministic fire/no-fire, severity, triggering-resource refs, source/version tag) — a discipline, not yet a shared engine.
- **F12 is an F6/F3 sibling and feeds F14.** F12 is the referral cousin of F6 (note assistant) and F3 (plain-language summary): the same generate → cite → review-before-use → never-auto-send spine, pointed at a destination template. **Downstream, F12 is the producer for the deferred F14 follow-up tracker** (`docs/f14-followup-tracker.md`) — it emits the `ServiceRequest` + `Task` (`Task.focus → ServiceRequest`, `Task.for → Patient`) that F14 consumes to track the referral to closure. That is a producer/consumer relationship, not a shared-infra coupling: removing F12 simply leaves F14 with no Tasks to track.
- **F13 is an F6/F3 sibling.** F13 is the paperwork cousin of the same two features — the identical generator spine pointed at a *structured form template* instead of free prose, reusing F6's `DocumentReference` + `Provenance` (`docStatus=preliminary` → `final`, never-AI-signed) write-back model and F3's facts-table + verbatim-post-check.

**Shared write broker.** F12 and F13 both write through the **same guarded `/api/fhir-write` broker F5 owns** (draft → explicit human confirm → submit + audit) — F12 for `ServiceRequest`/`DocumentReference`/`Task`, F13 for `DocumentReference`/`QuestionnaireResponse`/`Provenance` — adding **no new write machinery**. **F11 is the deliberate exception:** its egress is a flat claim file to a payer over MCEDT/EDT, not a FHIR write-back, so it stands up a **new feature-owned privileged route** (e.g. `/api/claim-submit`) that **copies the broker's draft→confirm→submit+audit *pattern*** but is genuinely new bespoke infra — and carries the governed de-id exception for the identifier-bearing claim file. All three route every draft/confirm/submit through `/api/audit`.

**The common "10x" theme.** All three move the clinician from **author to reviewer** on a high-friction, low-leverage transcription task: the chart already holds the facts (codes' justifying resources, the referral's demographics/problems/meds/allergies, the form's identifiers/dates/conditions), and today the clinician re-keys them by hand into someone else's layout — a fee-schedule claim, a portal-specific referral form, an insurer/agency document. The 10x in each case is **chart-grounded, cited prefill + a completeness check + a deterministic typed card the clinician reviews/edits/confirms**, beating an EMR built-in that, at best, offers a lookup box, an empty form, or a letterhead mail-merge — and never catches what's missing or closes the loop.
